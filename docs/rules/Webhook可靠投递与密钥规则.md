# Webhook 可靠投递与密钥规则

## 配置与地址

- 每个应用当前只维护一个启用中的 Webhook 配置，但地址变化必须创建地址版本对应的独立供应商端点，禁止把旧事件的重试改投到新地址。
- 每个供应商端点必须绑定只属于自己的 Channel；发布时必须指定当前配置记录中的端点 Channel，禁止向应用下全部历史端点广播。
- 地址只允许 DNS HTTPS URL；拒绝凭据、查询、片段、IP 字面量、本机和内部域名。输入校验不能替代投递端的 DNS 重绑定防护、私网阻断和 TLS 验证。
- 地址变化和密钥轮换必须自动停用通知、提升配置版本、清除旧测试状态并要求重新测试。
- 启用操作必须在后端校验“当前配置版本最近一次测试成功”，不能只依赖前端禁用开关。

## 事件与可靠性

- 只有实际异步执行的审核批次终态可以产生业务通知；同步路径不得发布。
- 审核终态与本地 Webhook 发布记录必须在同一业务事务中提交，供应商调用不得放在该事务内。
- 本地发布表必须有稳定业务去重键；并发领取使用数据库租约和 `SKIP LOCKED`，进程崩溃后租约可恢复。
- 提交供应商时使用发布记录 ID 作为稳定事件 ID 和幂等键。供应商已接受后只查询状态，不再从外层重新创建消息。
- 事件为至少一次语义。接收方必须按 `eventId` 或签名消息 ID 去重，Webhook 负载不得包含审核原文和密钥。
- 停用只影响新事件；已入队或已被供应商接受的事件继续完成，避免静默丢失。

## 密钥与审计

- 签名密钥只允许在首次配置、地址变化和主动轮换的单次写响应中返回，并设置 `Cache-Control: no-store`。
- 查询 DTO、React Query 缓存、持久浏览器存储、数据库审计负载和结构化日志不得出现完整签名密钥。
- 地址变化必须返回新端点的新密钥；相同地址的幂等保存不得重复回显密钥。
- 密钥轮换应支持可配置旧密钥宽限时间，但轮换后仍需停用、更新接收方并重新测试。
- 配置、启停、测试请求、地址变化和密钥轮换都属于关键写操作，必须记录不含敏感值的审计事实。

## 回归与部署门禁

- API 测试覆盖未配置、非法地址、首次密钥一次性返回、重复保存、测试状态、启用门禁、地址变化、轮换和权限。
- PostgreSQL 测试覆盖并发唯一配置、并发租约领取、失败重试和死信恢复，不能用内存数据库代替并发事实。
- 前端测试覆盖密钥不进入查询缓存、测试前不可启用、测试成功后可启用、地址草稿不被后台刷新覆盖和窄屏无横向溢出。
- 部署必须固定 Svix 版本，启用持久 Redis 队列、独立数据库、HTTPS-only 和健康检查；API readiness 不依赖 Svix。
- 生产验收必须使用真实公网 HTTPS 接收端完成验签、重复投递、非 2xx 重试、超时、DNS/私网阻断、停用在途消息和备份恢复演练。
